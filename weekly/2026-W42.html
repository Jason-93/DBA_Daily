一、本周 AI4DB / DB4AI / 稳定性雷达

1. AI4DB 务实转向：从「重写数据库」到「增强现有数据库」。

三条独立线索同向：JetStream 让 LLM 为固定负载合成带验证的专用查询加速器、嵌进现有系统（10-15 晨报）、DataKernelBench 检验 LLM 生成高性能 GPU kernel 的能力（10-16 晨报）、MySQL 内嵌 V8 JavaScript 引擎定位是扩展 SQL 而非搬走应用（10-16 晨报）。

AI 进数据库的叙事正在降温收敛——不再许诺替换引擎，而是嵌进查询计划、kernel 层、存储过程层做增强；评估 AI4DB 方案时，「能否嵌进现有系统并给出可信验证」正在取代「效果是否惊艳」成为第一问。

2. DB4AI 选型窗口收敛：向量检索进入「索引可扩展 × 过滤场景」正面交锋。

Timescale 开源 pg_vectorsearch，PRISM 索引在 1 亿向量上 6ms 返回、内存仅为 HNSW 的 1/4（10-14 晨报）；Weaviate 1.40 引入 SIGMOD 2026 论文作者贡献的自适应过滤策略 PathSeer（10-15 晨报）；Qdrant 出手修复 Perplexity 视觉检索器在 PDF 场景的体积与精度问题（10-14 晨报）；同期 Weaviate 修复 nearObject 跨集合向量泄露的中危漏洞（10-16 晨报）。

PG 扩展阵营与专用向量库阵营的代差在缩小，竞争点从「能不能用」移到「过滤场景性能与安全响应速度」——RAG 选型清单该加一列「安全 CVE 响应记录」，这周就是现成的提醒。

4. 云端并发控制的底层反思：MVCC 的默认地位开始被公开质疑。

arXiv 论文《The Case for Single-Version Concurrency Control in the Cloud》论证分离存储架构下多版本写放大、垃圾回收与长事务阻塞被放大，单版本并发控制重新占优（10-15 晨报）；同期 MySQL 宣布切换日历化版本模型，26.7 开启新纪元（10-13 晨报）。

当存储与计算分离成为默认，为共享磁盘时代设计的内核组件是下一个被逐个重写的对象——这类「重看默认设计」的论文是内功训练的优先精读项，比追新框架的边际收益高。

正方立论框架（组织有权强制拥抱 AI）

  1. 变革卡在协调困境，强制打破均衡：AI 转型是组织级协调博弈，等自愿采纳会永远停在「早期多数」之前；安全带、合规培训、安全生产都是先例——凡收益在集体层面而成本在个人习惯处的变革，最终都靠强制完成。
  2. 权责对称：一把手对经营结果负全责，就有权重置资源优先级；「必须」只是把一直存在的资源排序说透，比「提倡」式的模糊信号更诚实。
  3. 技能窗口期不等人：先用者获得复利，组织不推动等于把员工的未来竞争力让给竞争对手；「为你好」的父权逻辑在这里有真实成分——市场不会等待慢慢想通的人。

反方立论框架（理解不能被命令）

  1. KPI 化即能力空心化：「必须拥抱」产出的是表演性顺从——员工学会的是把 AI 用量演给考核看。阿伦特区分行动与顺从：被命令的「学习」替代了主动的理解，组织得到合规的姿势，失去真实的判断。
  2. 认知强制的悖论：理解恰恰是不能被强制的善；恐惧驱动的表面合规会抑制真实探索——员工不敢承认不会、不敢质疑工具的输出，反而制造新的风险面。
  3. 权力没有内置刹车：今天以效率为名强制拥抱，明天就可以强制别的什么；当「是否使用工具」都变成行政命令的对象，组织成员的自主空间被侵蚀得没有底线可引用（海德格尔的座架：一切被强求为「就绪的存货」）。

关联哲学文本

  • 阿伦特《人的境况》行动 vs 顺从：反方第 1 条的理论基石——行动始于自发的开端，顺从命令的「开始」不是行动；可对照你在读的《艾希曼在耶路撒冷》理解「不思考的服从」如何制度化。
  • 伯林《两种自由概念》积极自由的暴政：正方第 3 条本质是积极自由逻辑（「真正的你其实想要拥抱 AI」）——伯林本人对这种论证的批判可直接拆招；这也是本场最锋利的交锋点。
  • 海德格尔《技术的追问》座架（Gestell）：反方第 3 条——当效率成为唯一尺度，人和组织都被强求为「就绪的存货」；配合你的书单顺序，此文本就排期在读。
  • SEP 词条方向：Hannah Arendt（action / labor / obedience）；Positive and Negative Liberty（积极自由的家长主义论证与批判）；Paternalism（家长主义）；Philosophy of Technology（技术哲学导论）。

三、论文精读推荐

The Case for Single-Version Concurrency Control in the Cloud（arXiv 2610.15793）

arxiv.org/abs/2610.15793 · v1 提交于 2026-10 上旬（10-15 晨报技术层，评分 4.0）

导读：MVCC 是过去三十年数据库的默认答案——每个写操作产生新版本，读不加锁，隔离级别靠版本可见性实现。但论文指出：这套设计隐含「存储与计算共处一室」的假设；在云原生分离存储架构下，多版本带来的写放大、版本垃圾回收成本、长事务对清理的阻塞被同步放大，而共享存储让「单版本 + 集中式冲突仲裁」的古老方案重新变得划算。全文是一份完整的「默认设计重审」样本：先拆 MVCC 在云架构下的三条隐性成本曲线，再给单版本 CC 在分离存储上的可行性论证与代价边界。对 DBA 的价值不在「该不该换方案」，而在训练一种内功：你每天在用的隔离级别、锁等待、快照读行为，底层假设是可以被公开质疑的——本周 MySQL 日历化版本（10-13 晨报）与这篇论文同时出现，说明内核层的「重看默认」正在成批发生。

怎么读：先读引言对 MVCC 三条成本的拆解（15 分钟，这是全文问题意识的根），再读单版本方案在分离存储上的可行性论证（20 分钟）。建议对照团队在用引擎（Aurora / RDS PG）的实现文档，写一页备忘：「我们系统里哪些设计是共享磁盘时代的遗产、分离存储下各自的代价是什么」——这页备忘就是本期雷达第 4 条的落地动作。
